# v2.6.30 · 示例图本地永久缓存 + 视频首帧不再空白

两条直接反馈：**示例图每次都要重新从网上下载**，以及**模型播的是视频时首帧直接空白、详情页不显示，鼠标移过去才播，体验很割裂**。这一版把两条都修了，并在实测中抓到第三个只在真实库上才会现形的问题（纯视频模型的补帧看起来卡死）。

## 先说实测：为什么会空白、为什么会"卡住"

| 现象 | 实测 |
|---|---|
| 真实库 `images[]` 条目 | 479 条里 **107 条（22.3%）是 `.mp4`** |
| 这 107 条视频帧的 `imageUrl` | **100% 为空**（老 info 根本没这个字段）——没有现成的首帧图可用 |
| CDN 能否直接给首帧 JPEG | **不能**。`width=460` / `width=460,format=jpeg` / `resize=thumbnail` 三种写法返回的全部是 `content-type: video/mp4`（8,921,366 / 2,314,133 / 8,515,285 字节） |
| 一条视频原片 vs 它的 460 档 | 8.9MB ~ 19MB vs **2.3MB** |
| 示例图全是视频的模型 | 108 个有 info 的模型里 **19 个**；其中 3 个的原片已在盘上，**19 个全都缺首帧** |
| 远程帧的软件侧持久化 | 改之前是 **0**：`get_covers_multi` 只把 CDN 直链交给浏览器，第二次打开照样从头拉 |
| 浏览器抓帧回传写坏的一张 | `image_01.jpg` 357×640、**4307 字节、整张只有一个颜色**（标准差 0/0/0）；同一条帧由外壳取出是 **32045 字节、60829 个颜色** |
| `/api/media` 的白名单 | 真实配置 `media_roots` 为**空**、`models_dirs` **四个根**——本地模型视频换了同源地址照样 403 |

所以：首帧只能由程序自己从视频字节里解出来（纯 stdlib + PIL 解不了 H.264），而"要拿到首帧就得先下完整条视频"这个前提，正是"一直显示正在补齐示例图"的根因。

## 改了什么

1. **远程帧在软件侧留一份**：同一档字节永久落 `APP_DIR/detail_thumb_cache`，第二次打开直接出 `data:`、**零网络**。首屏 RPC 依然不"顺手补一张"——未命中只回一个 URL，另排一次后台入盘（单线程串行、同一 `档位:URL` 只排一次、上界 256 键）。代价如实写明：首次打开多花一份我们自己用的字节，换的是第二次以及以后每次。
2. **档位与缓存键统一到同一个数**：瀑布流 460、详情 512，且详情的 512 与前端随后那次 `get_cover_b64`（默认 512）同档；缓存键归一成「源图 URL + 档位」（`width=512` 与 `original=true` 是同一张图，各算各的键永远不命中）。两处一旦分叉，同一帧被取两次、落两份，第二次打开详情还多跑一趟网络。
3. **缩略图字节闸与 `config.image_max_mb` 解耦**（`_THUMB_FETCH_CAP=8MB`）。那个键管的是**原图归档**预算、能设到 1MB；此前拿它当缩略图上限，设置一低就 `len(data) > cap → return ""`，瀑布流与详情的缩略图**整片空白且毫不提示**。
4. **视频首帧由程序出像素**：新模块 `video_thumb.py` 走 Windows 外壳（`native/CftChrome.cs` 里 `SHCreateItemFromParsingName` + `IShellItemImageFactory::GetImage`，`IIGBF_RESIZETOFIT|IIGBF_THUMBNAILONLY`），长边 ≤640 的 JPEG，原子独占落盘、已有首帧绝不覆盖、目标或目录是重解析点就拒。落点复用既有补帧管线的新 kind：`<模型名>.images/image_XX.jpg`，与 `video_XX.mp4` **同序号**。PowerShell `Add-Type` 拿这个接口实测返回 `E_NOINTERFACE`，必须由 csc 编译的程序集声明 `InterfaceIsIUnknown` 且把 `GetImage` 排在接口首方法。
5. **首帧不等整条原片**（本轮实测抓出来的）。清单顺序统一成 **静帧 → 首帧 → 原片**；本地没有原片时，首帧自己另取一条 `width=460` 的小视频档当参考片（2.3MB 而不是 19MB），出帧后即删——参考片只落 `APP_DIR/video_probe`，**模型目录里只会出现 `image_XX.jpg`**，不会留下半个视频或临时文件。字节封 12MB、单条封 90s，取不到记"跳过（这一帧留到下次）"而不是失败。`_download_video` 每 256KB 把"正在下什么、已收多少 MB"写进任务状态，那行从此一直在动。
6. **消费侧三处一起接上**：`<video poster>`（详情主图 + 瀑布流叠帧）、自动轮播把带首帧静图的视频帧当静帧参与换帧（否则视频多的卡片在自动模式下整帧被跳过，看着就是呆的）、详情缩略条。`data:` 串绝不发给 `get_cover_b64`（那个 RPC 只认 http(s)，喂 `data:` 会拿到空串，前端于是把本来有图的缩略图整个 `remove()` 掉）。
7. **浏览器兜底模式的本地视频走 `/api/media`**：页面是 http origin 时 Chromium 一律拒绝 `file:///` 子资源（实测控制台 `Not allowed to load local resource`），而 v2.6.29 的「本地优先」把本地 mp4 直接写成 `src="file:///…"`——**这条模式下本地视频根本不播**（默认窗口模式同源可用，所以此前没暴露）。`_local_video_uri` 的注释当年写着"由前端降级远程 URL"，但那条降级从未实现。
8. **纯色伪首帧不再落盘，落了的修回来**：`readyState>=2` 不等于画布已经有画面——Chromium 在解出首帧之前 `drawImage` 不报错，端出来是一张纯黑，`toDataURL` 照样出图。这张图写进 `image_XX.jpg` 后有两层危害：用户看到的「首帧空白」变成「首帧一块黑」，而「本地已有首帧不覆盖」把后端外壳取帧这条真出路永久挡死（同一轮任务状态里就是 `done:1, failed:1`）。现在两侧同一判据（`≤4 个颜色` 或 `三通道标准差 <3`，按 64px 缩略统计）：前端发 RPC 前自查并退回「未试过」，后端写盘前拒收；盘上已有的纯色图按「还没补齐」重取一次（**每进程每帧只重取一次**——首帧本来就是黑场的淡入视频否则每次打开详情都要重下一条约 1.6MB 的参考片），排队与执行之间如果已经被写成一张真图就一帧都不碰。
9. **`/api/media` 白名单并入模型库根**：桥侧原来只认 `cfg["media_roots"]`，而第 7 条给出的路径是模型目录里的 `<名>.images/video_XX.mp4`——真实配置里 `media_roots` 为空，这一换反而 403，症状与没修一模一样，只是错误从浏览器的「被拒载」挪到了服务端的「无权访问」，只断言前者的验收会绿着漏掉。随同收进三条小修：`imageUrl` 指向 `.mp4` 的条目不再被当静帧排队（那种下载必败，还会让取帧分支永远进不去）、`image_(\d+)` 序号判定收成模块级一份、`get_cover_b64` 补上墙钟截止点（只有 socket 超时时，一条每次吐一点的慢流能钉死唯一的入盘 worker，`pending` 攒满 256 后整条缓存链路哑掉且不自愈）。

## 独立复核（第二轮）落地的 P0 / P1 / 七条 P2

- **P0**：补帧刚落盘就把视频从详情页挤掉。`get_model_detail` 按「本地图片张数」倒推占位序号，视频项的 `image_01.jpg` 也被算成一个静帧槽位，远程循环于是正好 `continue` 掉那条视频——而触发它的正是默认开启的首次打开补帧，等于改动自己删掉了自己要修的画面。
- **P1**：门禁在任何带 `build/native/CftChrome.dll` 的 Windows 机器上恒红（那条用例默认跟随 `video_thumb.available()`），现在显式给定。
- 七条 P2：封面与 poster 同一份字节出两次（载荷翻倍 + 把视频伪装成照片）；详情 460/512 同帧取两次；缩略图字节闸错误地跟着 `image_max_mb`；读侧缓存键没夹取；入盘队列 `put` 在锁外导致"worker 刚收工这一单才挂上"的孤儿（键永久留在 `pending`，攒满 256 后整条链路哑掉且不自愈）；原片没落成时首帧被记成第二次失败（一次故障说成两个坏消息，文案还把根因写成"本机取不到首帧"）；`poster_local` 前端从不消费。

## 已知代价与可调项

- 首次打开某个模型时，缩略帧会多一份我们自己用的字节（后台入盘），换第二次以及以后每次零网络。不想留就在设置里关掉「缓存详情图片」。
- 首帧参考片是**一次性的**：出完帧就删，不占模型目录空间，也不会被当成模型的视频文件。
- `images_dir_autofill` 默认**开**：这会往你的模型目录写 `image_XX.jpg` / `video_XX.mp4`。不想让软件动模型目录就在设置里关掉，或点详情那行里的取消；关闭只影响后续补帧，已落盘的帧保留。
- 非 Windows 上外壳不可用，首帧退回浏览器抓帧回传那条兜底路径（`file://` 页面画布会被污染，所以窗口模式下也可能拿不到）。

- Python 全量回归 **777 项通过、7 项跳过、68 组子用例**（本轮新增：纯色回传拒收、纯色旧图被真像素覆盖、纯色首帧按缺口重取且每进程只一次、`imageUrl` 指向 mp4 时不排静帧、`/api/media` 白名单含模型库根、纯色判据本身）。

最后一遍（r13）**PASS 15 项实机验收、退出码 0**；过程中撞红过三轮，三轮都是真信息：r8 抓到瀑布流入盘判据把远程 mp4 直链算成"没入盘"，r9 抓到纯色伪首帧（就是上表那行修复的由来），r11 抓到"字节进度"那次断言在赌首帧下载够慢。

验收脚本 `.tools/live_accept.cjs` 本身也在这几轮里被钉回来三处判据错误：把**远程 mp4 直链**当成"没入盘的缩略帧"（那条按设计就该远程）、把**视频流的 CDN 请求**算进"第二次零请求"的承诺、以及一处从未被执行到的变量名笔误。上一轮的 FAIL 之所以有价值，正是因为它换了一个纯视频目标模型——那条模型才把"回传一张纯黑"这个缺陷暴露出来。
